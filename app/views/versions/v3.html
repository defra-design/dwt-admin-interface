Design rationale

Kept here as a reference for later, so the reasoning behind these decisions is not lost between rounds of research.

Error messages in the “add another” pattern

Where the error sits: beside each field, naming that field

The error sits next to the individual email address field, not on the group as a whole. MOJ’s Add another component says to put the message beside the field and to name the item in it — their worked example is “Enter a first name for person 2”, shown next to that field and repeated in the error summary. Their errors example shows two fields in the same item each carrying their own message.

Naming the field is not decoration. The GOV.UK error summary requires messages to make sense out of context and to use identical wording to the inline message. With 5 fields, 4 identical lines saying “Enter an email address or remove the empty field” would be unusable. Numbered, each line is distinct and links to its own field.

Showing several errors at once, rather than one at a time

This is a deliberate divergence. MOJ says to “show errors for 1 item at a time using the GOV.UK error summary”, and DWP’s Add another thing says the same — validate items one by one.

That rule exists because an MOJ “item” contains several fields: a person is a first name, a last name and a date of birth, so 5 people could produce 15 messages. Here each item is a single field, capped at 5, so the worst case is 4 short messages mapping one-to-one onto 4 visible fields. Fixing them in one pass beats several rounds of submit-and-retry, and showing all errors together is what the GOV.UK validation pattern asks for generally. If research shows it is too much, switching to one at a time is a small change.

What the research does and does not cover

The GOV.UK error message and error summary components are well tested — users understood what went wrong and were able to recover — but that research is on single fields, not repeatable groups. MOJ’s Add another has been usability tested and externally accessibility audited, and MOJ, Home Office and DWP all say more research is needed. All three specifically flag research with users who have access needs on the “add another” step as the gap.

One finding is directly relevant: MOJ research found that cloning fields on a single screen can cause performance and validation problems, and makes it harder for users to fix errors as they go. That is why longer lists are steered towards MOJ’s Add to a list instead — one item per page, then a summary list. At a maximum of 5 we are well inside what Add another is for, but this is the reason not to raise the cap much.

Wording of the format error

The GOV.UK email addresses pattern gives “Enter an email address in the correct format, like name@example.com”. We use “for example” instead of “like”, which reads more naturally when spoken — backlog issue 47 is a team making the same argument, noting that the rest of the Design System site uses “for example”.

The example domain stays as example.com because RFC 2606 reserves it, so it can never belong to a real organisation or receive mail. This is why GDS and GOV.UK Notify use it — see backlog issue 45. Realistic-looking alternatives are usually real: company.co.uk and example.co.uk are both registered, and company.co.uk has live mail servers.

Confirming that a software provider has been added

There is no departmental pattern that says “when a civil servant adds a record to an internal list, always show a green banner”. The published guidance is about when not to use a confirmation page, and when a banner is an option.

The GOV.UK confirmation page is for the end of a transaction — “Application complete”, a reference number, what happens next. The confirmation pages backlog is explicit that a green confirmation screen is for when the user has successfully finished. Using one here would tell someone they are done, when they have only added one item to a list they may keep working on.

The GOV.UK notification banner (success variant) is the component GDS offers for “the outcome of something they’ve just done on a previous page” when they have not finished the current journey. The NHS service manual is more specific: use a success banner for steps in a long journey or small repeated tasks, and remove it when the user moves on. MOJ’s experimental confirm an action pattern says that if the action does not need a confirmation screen, a notification is shown immediately after. None of this is research with civil servants adding records to an admin list — it is guidance written for transactional public services and then reused.

The “Edit a list” backlog item (also known as add to a list) describes the expected outcome as: the newly added item appears in the list, with Change and Remove. HMRC research on that pattern with internal users was about adding many organisations quickly and returning to the list, not about needing a banner to confirm each add.

We have gone with the list itself as the confirmation: newest first, today’s date on the new row. That matches what you expected and what the add-to-a-list research describes. A banner is still the published GDS/NHS/MOJ option if research shows people miss the new row — it is easy to put back. A confirmation page would be the wrong pattern either way.

The company detail page

MOJ’s case list says: put the link in the first column, use the name (not “View”), and keep further actions off the list and on the details page. MOJ’s identity bar is for a case with several subsections. We have one details page, so the heading is the company name with “Software providers” as the caption, and a back link.

GOV.UK’s summary list is the pattern for showing a record as key facts, including in caseworking systems (summary cards are for several lists of the same type on one page — we only have one). Each editable row has a Change link that goes to that question, which is also how DWP’s add another thing and MOJ’s add another tell you to let users edit after submit. Notes have no Change link: they are an audit record. They sit in MOJ’s timeline, newest first, which is the caseworking pattern for dated events. There is no published Home Office “case details” page — their add multiple things pattern is a loop onto a summary list, which is the same idea at a smaller scale.

The empty state on the Software providers list

GOV.UK has no empty state pattern — it is still an open item in the Design System backlog. The nearest published guidance is the ONS table component: replace an empty table with a line of plain text, “No [what the table shows]”. The backlog discussion adds that an empty state should also say what will be there, so the page says both. The table header row is hidden when there is nothing in it, because a bare header with no rows reads as broken.

Server-side “add another”, not the MOJ JavaScript

The component is built as HTML rather than with the mojAddAnother macro, and without data-module="moj-add-another", so adding and removing fields happens on the server. This is the no-JavaScript baseline MOJ describes. It matters because MOJ’s JavaScript adds fields in the browser, which would happily add a sixth address and the maximum-of-5 error would never fire.

One quirk this inherits from the real MOJ component: pressing Enter inside a text field triggers the first submit button in the form, which is “Add another email address” rather than “Save”. The result is a spare blank field the user can remove, so it is recoverable — but worth watching for in research.
