Design rationale

This version is not tested with users. It is built from the October 2026 task flows, which are partly unverified. It is a concept to discuss with the service team and stakeholders, not a specification.

This version has its own session data. Changes made in this version are not shown in any other version, and the other way round.

Patterns from other departments

  • Eight things I’ve learnt from designing services for colleagues (DWP Digital): design for repetition, let the “one thing” on a page be larger for staff, and keep everything needed to answer an enquiry in one place. This is why a change and its reason are on one page, and why the case file Overview brings the details, contacts, software packages and latest history together.
  • Designing caseworking systems meetup 2 (cross-government): persistent navigation, important information on the overview, and history entries that are labelled and can be filtered. This is why the case file has Overview, Contacts and History as pages with the same navigation, a reminder on the Overview, and a type on each history entry.
  • Filter a data table (a pattern proposed for the Home Office design system): search, filters and a data table work as one pattern, and staff should not need filters for tasks they repeat. This is why the home page links to each status with a count. It is a proposal, not a published pattern.
  • Search for something (Home Office): a wide search when staff may only have part of the information, and a button to apply filters. This is why one search box covers the organisation, reference, software package, client name, client ID and contact.
  • Filter a list (MoJ), with the MoJ filter, sortable table, sub navigation, identity bar, timeline, alert, interruption card and scrollable pane, which are made for internal services. GOV.UK components are used for everything else, including the task list for an audit.

Differences from earlier versions and from the MoJ patterns

  • After an action, the next page shows an MoJ success alert, as version 9 does on its list and software provider pages. There are no confirmation panel pages, because staff carry on working in the case file.
  • The MoJ filter component is used, but not the MoJ “filter layout”, which hides the filter behind a button with JavaScript. The filter is always shown, in a GOV.UK grid.
  • The MoJ identity bar is made for the full width of the screen. A small style lines it up with the page.
  • The environment for new credentials comes from the button on the software package page. There is no “which environment?” question to get wrong.
  • “Check your answers” pages are used where a journey has several steps or cannot be undone: creating a case file, creating credentials and replacing a secret.
  • “Are you sure?” pages (MoJ interruption card, as in version 9) are used for removing a software provider, revoking access and moving a software package.
  • Statuses are tags with words, never colour alone: Created (grey), In test (blue), Approved for production (teal), In production (purple), Suspended (orange), Revoked (red) and Closed (grey).

Assumptions to confirm

  • How staff check that a contact can act for a software provider. There is no policy, so the methods offered are examples.
  • The values for provider type, developer type and size. They are placeholders for the columns in the team spreadsheet.
  • A secret is sent as a one-time link by email. The software provider’s side is not built, and “sent” is the only delivery status.
  • After a security breach, the service tells a Defra security team mailbox automatically.
  • Access can be suspended without changing the secrets.
  • Client names are made by the service and do not change when an organisation is renamed or a software package moves.
  • A message to a group of software providers is sent from a team mailbox, not by this service.
  • An audit is 10 random actions, and one audit is under way at a time.
  • A removed software provider’s case file is kept. How long to keep contacts’ personal details needs a decision.
  • Both roles are needed. Whether an auditor should see contact details has not been decided.

Not built

  • Allocation, which is out of scope.
  • The production approval test submissions (the link goes to a placeholder page), and approval for each API capability.
  • Service metrics, a view of data quality, and nudging a software provider who is stuck, apart from the “Days in status” column.
  • Real sign-in, session time-out, and paging for long lists.
  • The Waste organisations report is copied from version 9 without changes.

Risks to test first

  • Sending secrets straight to a contact, checking contacts and audit are the least certain parts. Test them with the service team first.
  • Six statuses, and a reason on every change, both add work for staff. GOV.UK guidance is to start with the fewest statuses you can.
